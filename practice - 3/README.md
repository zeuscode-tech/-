# Практическая работа № 3 — Процессы в Linux

Вариант B.

## 1. Дерево процессов

ptree.py читает /proc/<PID>/status без использования ps.
Отбирает процессы текущего пользователя по UID.
Выводит PID, состояние, RSS в КиБ и имя.
Отступами показывает отношения родитель — ребёнок.

Процессы могут завершаться во время обхода /proc,
поэтому ошибки чтения обрабатываются.
Процессы без родителя в выбранном наборе выводятся как корни.

Результат: [ptree_output.txt](ptree_output.txt).

## 2. Запуск процессов

runner.py создаёт N детей через os.fork().
Каждый ребёнок вызывает os.execvp(), заменяя свою программу
переданной командой. Родитель собирает результаты через waitpid.

Три запуска sleep 2 завершились с кодом 0:
- PID 4790 — 2.010 с;
- PID 4791 — 2.010 с;
- PID 4792 — 2.010 с.

Процессы работали параллельно.
Два запуска sh -c 'exit 7' вернули код 7.

Измеряется время от момента перед fork до получения результата
через waitpid. Оно включает запуск и задержку ожидания родителя,
а не только процессорное время ребёнка.

Результаты:
[runner_output.txt](runner_output.txt),
[runner_exit7.txt](runner_exit7.txt).

## 3. Зомби

Ребёнок завершился, но родитель временно не забирал его статус.

Вывод ps до waitpid:

## 4. Сирота

Исходный родитель PID 4858 завершился раньше ребёнка PID 4859.

Вывод ps после смены родителя:

    PID    PPID S COMMAND
    2327      1 S /usr/lib/systemd/systemd --user
    4859   2327 S python3 orphan.py

В этой системе сироту усыновил systemd --user, PID 2327,
выступающий в роли subreaper, а не непосредственно PID 1.

Скрипт разрешил ребёнку завершиться и проверил его исчезновение.
Оба демонстрационных процесса отсутствовали после выполнения.

Результат: [orphan_output.txt](orphan_output.txt).

## 5. Ленивое копирование памяти

Родитель создал список из 8 000 000 элементов.
После fork ребёнок заменил все элементы унаследованного списка.

| Показатель ребёнка | До, КиБ | После, КиБ | Изменение, КиБ |
|---|---:|---:|---:|
| RSS | 71640 | 71832 | +192 |
| PSS | 34777 | 66103 | +31326 |
| Private_Dirty | 400 | 62956 | +62556 |

После fork страницы изначально разделяются родителем и ребёнком.
При записи механизм copy-on-write создаёт частные копии страниц.

RSS почти не изменился: он учитывает и общие резидентные страницы.
Рост Private_Dirty примерно на 61 МиБ показывает появление
частных изменённых страниц. PSS вырос, поскольку страницы списка
теперь учитываются у ребёнка полностью, а не как доля общих.

Небольшая часть изменений памяти связана с работой интерпретатора
и самими измерениями.

Ребёнок завершился с кодом 0.
Список родителя остался неизменным: True.

Результат: [cow_output.txt](cow_output.txt).

## Контрольные вопросы

### Почему fork возвращает два разных значения?

После успешного fork выполнение продолжается в двух процессах.
Родитель получает PID ребёнка, а ребёнок — 0.
Это позволяет различить ветки выполнения.
При ошибке системный вызов возвращает -1; в Python os.fork()
вызывает исключение OSError.

### Что изменится, если вызвать exec без предварительного fork?

Текущая программа будет заменена новой в том же процессе.
PID сохранится, новый процесс не создаётся.
При успешном exec выполнение старой программы не продолжается.
Поэтому без fork не останется отдельного родителя,
который мог бы ждать запущенную команду.
